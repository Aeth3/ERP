# AR Invoices & Progress Billing — Design Spec

**Date:** 2026-11-05
**Status:** Approved design (roadmap step 4)
**Depends on:** Finance/GL core (LedgerPostingService), AP bills/payments (step 3 — patterns mirrored throughout)

## Purpose

Record what customers owe us and collect it, posting to the general ledger:

1. **Sales order invoices** — bill a customer for goods already shipped on a sales order, recognizing Sales - Materials revenue (COGS was already posted at shipment).
2. **Project progress billings** — bill a construction project's customer a percentage of the contract (or a peso amount), recognizing Contract Revenue, with part of each billing withheld as retention.
3. **Receipts** — collect cash/bank/check against open invoices, mirror of AP payments.
4. **AR aging** — who owes what, bucketed by days overdue.

Out of scope: customer downpayments/advances (account 2200), output-VAT split (step 5), milestone/billing schedules, statements and dunning, bad-debt provisions, credit memos.

## Decisions (user-approved)

- Both invoice kinds in one module: SO-backed invoices and project progress billings.
- Progress measurement: add `contractAmount` to `Project`; each billing is a % of contract or a peso amount; cumulative billed must not exceed the contract.
- Retention: per-project `retentionRate`; each progress billing splits into AR due and Retention Receivable; a retention-release action converts withheld retention into a collectible invoice.
- Receipts: simple, mirroring AP payments (allocations across open invoices, method CASH/BANK/CHECK).
- Placement: inside `modules/finance`, alongside AP (established pattern). Finance reads other modules only through ports.
- Money rules carried forward: PHP, VAT-inclusive, BigDecimal scale ≤ 2, HALF_UP; business zone Asia/Manila; revenue on billed basis.

## Domain model (modules/finance/domain)

### Enums

- `InvoiceKind`: `SALES_ORDER`, `PROGRESS_BILLING`, `RETENTION_RELEASE`
- `InvoiceStatus`: `DRAFT`, `APPROVED`, `PARTIALLY_PAID`, `PAID`, `CANCELLED` (same lifecycle as `BillStatus`; CANCELLED only while nothing received)
- Reuse `PaymentMethod` (CASH/BANK/CHECK) for receipts.
- `JournalSourceType`: add `AR_INVOICE`, `AR_RECEIPT`.
- `AccountMappingKey`: add `ACCOUNTS_RECEIVABLE` (1100), `RETENTION_RECEIVABLE` (1110), `SALES_REVENUE` (4100 Sales - Materials), `CONTRACT_REVENUE` (4000). All four accounts already exist in the CoA; `FinanceSetupService.ensureDefaults()` adds the mappings idempotently.

### Invoice (`ar_invoices`)

| Field | Notes |
|---|---|
| id | UUID |
| invoiceNumber | generated `ARI-yyyyMM-nnnn` (Asia/Manila month of invoiceDate), unique column; prefix-count + existsByInvoiceNumber skip loop, same as PAY numbers |
| kind | InvoiceKind |
| customerId | required |
| salesOrderId | required iff kind = SALES_ORDER |
| projectId | required iff kind = PROGRESS_BILLING or RETENTION_RELEASE |
| invoiceDate, dueDate | dueDate nullable (aging falls back to invoiceDate) |
| status | InvoiceStatus |
| subtotal | sum of line totals |
| retentionAmount | ≥ 0; non-zero only for PROGRESS_BILLING |
| total | collectible amount = subtotal − retentionAmount (for SALES_ORDER and RETENTION_RELEASE, total = subtotal) |
| amountReceived | cumulative receipts allocated |
| journalEntryId | set at approval |
| notes, createdBy, createdAt | as Bill |
| lines | List\<InvoiceLine\>, EAGER, cascade, orphanRemoval, @OrderBy lineNumber |

`amountReceived` tracks against **total** (the collectible amount), not subtotal: retention is not due until released.

### InvoiceLine (`ar_invoice_lines`)

| Field | Notes |
|---|---|
| id, invoiceId, lineNumber | |
| salesOrderItemId | SALES_ORDER kind only |
| productId | copied from SO snapshot at draft (SALES_ORDER kind) |
| description | required for PROGRESS_BILLING / RETENTION_RELEASE lines |
| quantity, unitPrice | SALES_ORDER kind; ≤ 2 dp |
| lineTotal | SALES_ORDER: quantity × unitPrice (scale 2 HALF_UP); others: entered amount |

A progress billing has exactly one line (description + amount). A retention-release invoice has exactly one line, generated by the release action.

### Receipt (`ar_receipts`) + ReceiptAllocation (`ar_receipt_allocations`)

Exact mirror of Payment/PaymentAllocation: receiptNumber `RCT-yyyyMM-nnnn`, customerId, receiptDate, method, reference, total, journalEntryId, createdBy/At, allocations (invoiceId, amount).

### Repositories (domain/repository, interfaces)

- `InvoiceRepository`: save, findById, findByIdForUpdate (PESSIMISTIC_WRITE), findBySalesOrderId, findByProjectId, search(customerId, status, kind — all nullable), existsByInvoiceNumber, findOpen (APPROVED + PARTIALLY_PAID).
- `ReceiptRepository`: save, findById, findByCustomerId, findAll, existsByReceiptNumber.

### Persistence

Entities + impls + JPA repos in `infrastructure/persistence/{entity,impl,jpa}` following the Bill pattern. Migration `V20261105_02__accounts_receivable.sql`, idempotent: `ar_invoices`, `ar_invoice_lines`, `ar_receipts`, `ar_receipt_allocations`, plus `ALTER TABLE projects ADD COLUMN IF NOT EXISTS contract_amount numeric(14,2)` and `retention_rate numeric(5,2)`. Unique index on `ar_invoices.invoice_number` and `ar_receipts.receipt_number` (our generated numbers — no supplier-scoped partial index needed). Never edit old migrations; JPA entities carry the same columns for ddl-auto.

## Project changes (modules/project)

- `Project` gains `contractAmount` (nullable BigDecimal) and `retentionRate` (nullable BigDecimal, percent 0–100, ≤ 2 dp). Entity, domain model, DTOs, create/update service paths, and frontend project form gain the two fields. Null contractAmount means the project cannot be progress-billed yet; null retentionRate means 0.

## Ports (modules/finance/application/port)

- `SalesOrderReader`: `Optional<SoSnapshot> find(UUID salesOrderId)`;
  `record SoSnapshot(UUID id, String soNumber, UUID customerId, String status, List<SoLine> lines)`;
  `record SoLine(UUID soItemId, UUID productId, String productName, BigDecimal quantity, BigDecimal returnedQuantity, BigDecimal unitPrice)`.
  Implemented by `modules/inventory/infrastructure/adapter/FinanceSalesOrderReader` (SalesOrderRepository, SalesOrderItemRepository, SalesReturnRepository, SalesReturnItemRepository, ProductRepository). Returns are product-level: allocate greedily across duplicate-product SO items, same algorithm as `FinancePurchaseOrderReader`.
- `ProjectBillingReader`: `Optional<ProjectSnapshot> find(UUID projectId)`;
  `record ProjectSnapshot(UUID id, String projectCode, String projectName, UUID customerId, String status, BigDecimal contractAmount, BigDecimal retentionRate)`.
  Implemented by `modules/project/infrastructure/adapter/FinanceProjectBillingReader`.

## Services (modules/finance/application/service)

### ArInvoiceService

Constructor: InvoiceRepository, SalesOrderReader, ProjectBillingReader, LedgerPostingService, AccountMappingRepository, `@Value finance.time-zone`.

Requests: `CreateInvoiceRequest(kind, customerId, salesOrderId, projectId, invoiceDate, dueDate, notes, List<LineReq>)`, `LineReq(salesOrderItemId, quantity, unitPrice, amount, description)`. For PROGRESS_BILLING the caller sends either `amount` (pesos) or a percent — the frontend converts percent to pesos before submit; the API accepts pesos only.

- `createDraft` / `updateDraft` (draft only, findByIdForUpdate on update):
  - SALES_ORDER kind: SO must exist via reader; customer must equal SO customer; every line's salesOrderItemId must belong to the SO; productId and unitPrice default from the snapshot (caller may override unitPrice); quantity > 0, ≤ 2 dp.
  - PROGRESS_BILLING kind: project must exist via reader, status ACTIVE, contractAmount set; exactly one line with positive amount ≤ 2 dp; retentionAmount = amount × retentionRate / 100 (scale 2 HALF_UP); customer must equal project customer.
  - RETENTION_RELEASE: not creatable directly — only via `releaseRetention`.
- `approve(id)` (findByIdForUpdate):
  - SALES_ORDER: SO status must be SHIPPED or DELIVERED; cumulative invoiced quantity per SO item across non-CANCELLED invoices of the SO, including repeated lines in this invoice (`alreadyInvoiced.merge`), must not exceed shipped quantity net of returns (= ordered − returned, since shipping is whole-SO). Error message names the product.
  - PROGRESS_BILLING: cumulative billed subtotal across non-CANCELLED progress billings of the project, plus this one, must not exceed contractAmount.
  - RETENTION_RELEASE: re-compute releasable at approve time excluding this invoice; this invoice's subtotal must not exceed it (two drafts cannot double-release).
  - Posts the journal entry (below), sets journalEntryId, status APPROVED.
- `cancel(id)`: draft → CANCELLED without posting; approved with amountReceived = 0 → reverse journal entry, CANCELLED; anything received → reject ("has receipts"); already cancelled → distinct message. A cancelled RETENTION_RELEASE restores the project's releasable retention (derived, nothing to write back).
- `releaseRetention(projectId, invoiceDate, dueDate)`: releasable = Σ retentionAmount of non-CANCELLED progress billings − Σ subtotal of non-CANCELLED RETENTION_RELEASE invoices for the project; must be > 0. Creates and returns a DRAFT RETENTION_RELEASE invoice with one line ("Retention release — <projectCode>", amount = releasable). Approval posts Dr AR / Cr Retention Receivable.
- `get`, `search(customerId, status, kind)`, `invoiceableLines(salesOrderId)` → `InvoiceableLine(soItemId, productId, productName, shippedQuantity, returnedQuantity, invoicedQuantity, remainingQuantity, unitPrice)`, `projectBillingSummary(projectId)` → `ProjectBillingSummary(projectId, projectCode, contractAmount, retentionRate, billedToDate, retentionHeld, retentionReleased, remainingContract)`.

### Journal entries (all via LedgerPostingService.post, entryDate = invoiceDate/receiptDate)

| Event | Debit | Credit |
|---|---|---|
| SALES_ORDER invoice approve | ACCOUNTS_RECEIVABLE total | SALES_REVENUE total |
| PROGRESS_BILLING approve | ACCOUNTS_RECEIVABLE (subtotal − retention), RETENTION_RECEIVABLE retention | CONTRACT_REVENUE subtotal |
| RETENTION_RELEASE approve | ACCOUNTS_RECEIVABLE total | RETENTION_RECEIVABLE total |
| Receipt create | CASH or BANK (CHECK→BANK) total | ACCOUNTS_RECEIVABLE total |

Memo: "Invoice <number>" / "Receipt <number>". sourceType AR_INVOICE / AR_RECEIPT, sourceId the invoice/receipt id. Zero retention lines are omitted (no zero-amount journal lines).

### ArReceiptService

Mirror of ApPaymentService: `create(CreateReceiptRequest(customerId, receiptDate, method, reference, List<AllocationReq(invoiceId, amount)>))` — validates positive ≤ 2 dp amounts, findByIdForUpdate per invoice, customer match, status APPROVED/PARTIALLY_PAID, merged per-invoice allocation ≤ remainingDue (total − amountReceived); saves receipt, posts, updates invoices' amountReceived/status (PAID when amountReceived ≥ total). `get`, `search(customerId)`. Receipt number `RCT-yyyyMM-nnnn` with skip loop.

### ArAgingService

Mirror of ApAgingService over open invoices: `aging()` / `aging(LocalDate asOf)` → `AgingRow(customerId, current, days1To30, days31To60, days61To90, over90, total)` on remaining due; null dueDate → invoiceDate.

## API (presentation/controller/ArController, @RequestMapping("/finance/ar"))

- `POST /invoices`, `PUT /invoices/{id}`, `POST /invoices/{id}/approve`, `POST /invoices/{id}/cancel`, `GET /invoices?customerId&status&kind`, `GET /invoices/{id}`
- `POST /projects/{projectId}/release-retention`
- `GET /invoiceable?salesOrderId`
- `GET /projects/{projectId}/billing-summary`
- `POST /receipts`, `GET /receipts?customerId`, `GET /receipts/{id}`
- `GET /aging`

Security: covered by the existing `/finance/**` role matcher (FINANCE, ADMIN). PermissionCatalog adds `finance.ar.read`, `finance.ar.manage` to allPermissions + financePermissions.

- `types/finance.ts`: InvoiceKind, InvoiceStatus, InvoiceLineDto, InvoiceDto, CreateInvoicePayload, ReceiptDto/CreateReceiptPayload, ArAgingRowDto, InvoiceableLineDto, ProjectBillingSummaryDto.

- `components/finance/receipts-tab.tsx`: mirror of payments-tab across open invoices with Pay-in-full.
- `components/finance/ar-aging-card.tsx`: mirror of ap-aging-card.
- `pages/finance.tsx`: add Invoices / Receipts / AR Aging tabs.
- Project form: add Contract amount and Retention % fields.

## Error handling

BadRequestException with user-readable messages (named product / invoice number in match and allocation errors), NotFoundException for missing aggregates — surfaced by GlobalExceptionHandler as 400/404, same as AP.
